# 設計メモ

## 全体像

```
                 ┌──────────── scripts/build_index.py ────────────┐
 文書フォルダ ──▶ │ 抽出 (extract) → トークン数で分割 (chunking)    │
                 │ → bge-m3 で埋め込み → FAISS (flat_sq8)          │
                 │   + state.sqlite (files / chunks)               │
                 └──────────────────┬─────────────────────────────┘
                                    │
 質問 ──▶ Retriever.search ─────────┤  1. 密検索: bge-m3 + FAISS で候補 200 件
                                    │  2. リランク: bge-reranker-v2-m3 (sigmoid で 0..1)
                                    │  3. MMR (任意) → 4. 足切り (任意) → top_k
                                    ▼
          ┌──────── RAG チャット ────────┐   ┌──────────── エージェント ────────────┐
          │ 番号付きコンテキスト + 質問   │   │ ReAct: LLM が JSON で道具を選ぶ        │
          │ → LLM (OpenAI 互換) で回答   │   │  search_docs / find_tables / describe │
          └──────────────────────────────┘   │  / sample_rows / explain / query /    │
                                             │  make_chart → 観測 → … → 最終回答     │
                                             └───────────────────────────────────────┘
 評価: scripts/eval_rag.py  build-golden (LLM がチャンクから質問を合成) → run (FILE@k / CHUNK@k / MRR)
```

## 主な設定

| 項目 | 中身 |
|---|---|
| チャンク分割 | bge-m3 のトークナイザで 512 トークン・重なり 64 |
| 埋め込み | bge-m3、fp16、max_seq_length 1024、正規化 |
| 索引 | FAISS IndexIDMap2(ScalarQuantizer 8bit, 内積)。flat / flat_fp16 も選べる |
| 密検索の候補数 | 200 |
| リランカー | bge-reranker-v2-m3、fp16、max_length 1024、sigmoid |
| MMR・足切り | 実装あり・既定 off |
| 絞り込み | SQLite で ID を解決 → FAISS の IDSelector (拡張子・パス) |
| 状態 DB | files / chunks (chunk_id = FAISS の ID) |
| 評価 | チャンク → LLM が質問を合成、(path, chunk_index) をラベルに FILE@k / CHUNK@k / MRR |
| エージェント | JSON の ReAct、形式エラー・繰り返しの打ち切り、観測の切り詰め、記録に無い数値の警告、原因調査モード |
| DB | SQLite (mode=ro + 文の検査 + 認可コールバック + 実行時間の上限) |
| LLM | Ollama (ネイティブ API) か OpenAI 互換 API (vLLM / LM Studio …) |
| 規模 | 数千〜数万チャンク、1 台の PC |
| データ | ウィキペディア (公開) + 架空の工場のデータ |

### 範囲外

ログイン・権限・監査ログ、会話の保存、定期的な自動ビルド、検索サーバの分離、資料の生成、
Python を書いて実行するエージェント、音声認識・画像生成、Web 検索。

## 判断の理由

- **評価のラベルは (path, chunk_index)。** chunk_id は AUTOINCREMENT なので、作り直すと番号が振り直され、
  質問集は正しそうに見えたまま点数だけが崩れる。
- **主指標は FILE@k。** リランカーを強くすると、正解チャンクの隣のチャンク (同じくらい答えになる) を上げることが
  ある。CHUNK@k だけ見るとそれを「悪化」と読み違える。
- **評価の 1 問の失敗は「外れ」として記録し、全体を止めない。** 1 問のせいで 99 問の測定を捨てない。
- **絞り込みは検索の前に ID で。** 上位 N 件を取ってから捨てると、少数派の文書 (全体の数 % しかない
  種類の文書など) を絞り込んだときに候補がほとんど残らない。
- **リランカーのスコアは sigmoid で 0..1 にする。** 足切りの閾値を解釈できるように。
- **エージェントに function calling を要求しない。** 小さいローカルモデルでも動くよう、道具の一覧と返答の
  形式をプロンプトに書き、JSON を読む。形式エラー・同じ呼び出しの繰り返し・手数の上限で打ち切る。
- **最終回答は「成功した手順の記録」だけを根拠に書かせ、記録に無い数値を警告する。** 小さいモデルは
  見えない値を推測で書くことがある。成功した手順が無ければ LLM に書かせず
  定型文で答える。
- **最終回答に渡す記録は、値を返した手順に多く割り振る (allocate)。** 均等に割ると、手数が多いときに肝心の
  集計結果まで切られる。
- **グラフは LLM に Python を書かせず、種類・列の指定だけを受けて決まったコードで描く。**
